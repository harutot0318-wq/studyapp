1. このアプリの全体像

このアプリは大きく2つの部分でできています。

  • フロントエンド兼バックエンド：Next.js（web/フォルダ）。画面の表示と、データベースとのやり取りの両方をこの1つのプロジェクトが担当します
  • データベース：Supabase（PostgreSQL）。ユーザー情報・資格・科目・教材・単語などのデータを保存します

昔ながらのWebアプリだと「フロントエンド（React）」と「バックエンド（API）」を別々に作ることが多いですが、Next.jsは1つのプロジェクトの中で両方を書けるのが特徴です。この仕組みを支えているのが「サーバーコンポーネント」と「Server Actions」という機能で、次の章で説明します。

2. 知っておくと読みやすくなる4つの概念

2.1 サーバーコンポーネント と クライアントコンポーネント 重要

Next.jsのコンポーネント（画面の部品）には2種類あります。

サーバーコンポーネントクライアントコンポーネント
動く場所サーバー側だけブラウザ側（ユーザーのPC）
書き方何もつけない（デフォルト）ファイルの先頭に"use client"と書く
できることデータベースに直接アクセスできるクリックなどのイベント処理、ブラウザのAPI利用
このアプリでの例ほぼ全ページ（page.tsx）グラフ（bar-chart.tsx）、サイドバーの現在地表示（nav-sidebar.tsx）

このアプリはほとんどがサーバーコンポーネントです。理由はシンプルで、「今どの資格が選ばれているか」「単語一覧」などのデータは全部データベースにあり、それをそのままサーバー側で取得して表示すればよいからです。ブラウザ側で動くJavaScriptが少なくて済むので、ページの表示も速くなります。

逆に、グラフ描画ライブラリ（Recharts）はブラウザの画面サイズを見ながら描画する必要があるため、これだけは"use client"をつけたクライアントコンポーネントにしています。

読むときのコツ： ファイルの先頭に"use client"があるかどうかを確認するだけで、「これはブラウザで動くコードか、サーバーでしか動かないコードか」がすぐ分かります。

2.2 Server Actions（フォーム送信 = サーバー関数呼び出し）

普通のWebアプリでは「フォームを送信する」→「APIにリクエストを送る」→「APIがデータベースを更新する」という3ステップを自分で書く必要があります。Next.jsのServer Actionsという機能を使うと、これを1ステップで書けます。

例：タスク追加フォーム（簡略化）
// page.tsx（画面）
<form action={createTask}>
  <input name="title" />
  <button type="submit">追加</button>
</form>

// actions.ts（サーバー側で実行される関数）
"use server";
export async function createTask(formData: FormData) {
  const title = formData.get("title");
  await supabase.from("tasks").insert({ title });
}

<form action={createTask}>と書くだけで、フォーム送信時にcreateTask関数がサーバー側で実行されます。ボタンを押す→データベースに保存、の間にAPIを自分で作る必要がありません。ファイルの先頭に"use server"と書かれている関数がServer Actionsです。

2.3 Supabaseとの接続（2種類のクライアント）

このアプリではsrc/lib/supabase/フォルダに、データベースへの接続を作る関数が2つあります。

  • client.ts：ブラウザ側から使う用（今回はほぼ未使用）
  • server.ts：サーバー側（ページ・Server Actions）から使う用。ほぼ全部の機能がこちらを使っています

なぜ分かれているかというと、ログイン情報（Cookie）の読み書き方法がサーバー側とブラウザ側で違うためです。server.tsはnext/headersのcookies()を使ってCookieを読み書きします。

2.4 RLS（Row Level Security）

データベース側の安全装置です。全テーブルに「user_idが自分のIDと一致する行しか見えない・操作できない」というルールがかかっています。これにより、アプリのコードに多少バグがあっても、他人のデータが見える・書き換えられるという事故がデータベース側で防がれます。詳しくはデータ設計書の「RLS方針」を参照してください。

3. 1つの機能を最初から最後まで追ってみる（タスク管理）

概念だけだと分かりにくいので、実際に「タスク管理」画面が表示されるまでの流れを、コードを見ながら追います。

ステップ1：URLにアクセスすると何が動くか

/tasksにアクセスすると、まずsrc/app/(app)/layout.tsxが実行されます。これは(app)フォルダ配下の全ページに共通する「外枠」です。

src/app/(app)/layout.tsx（抜粋）
const supabase = await createClient();
const { data: { user } } = await supabase.auth.getUser();

if (!user) {
  redirect("/login");   // ログインしていなければログイン画面へ
}

return (
  <div className="flex min-h-screen bg-gray-50">
    <aside>...サイドバー...</aside>
    <main>{children}</main>   ← ここに各ページの中身が入る
  </div>
);

ここでログインチェックをしているので、個別のページ側ではログインチェックを書かなくてよいことに注目してください。これはNext.jsの「レイアウトは配下の全ページに自動的にかぶさる」という仕組みを利用しています。

ステップ2：データ取得（lib/tasks/queries.ts）

src/lib/tasks/queries.ts
export async function getTasks(examId: string): Promise<Task[]> {
  const supabase = await createClient();
  const { data, error } = await supabase
    .from("tasks")
    .select("id, title, priority, is_done")
    .eq("exam_id", examId)
    .order("is_done", { ascending: true })
    .order("created_at", { ascending: false });

  if (error) throw error;
  return data;
}

.from("tasks")で「tasksテーブルを見る」、.eq("exam_id", examId)で「今の資格のタスクだけに絞る」、.order(...)で並び順を指定しています。SQLを直接書かなくても、こういうメソッドチェーンでクエリを組み立てられるのがSupabaseクライアントの特徴です。

ステップ3：画面に表示する（tasks/page.tsx）

src/app/(app)/tasks/page.tsx（抜粋）
export default async function TasksPage() {
  const activeExam = await getActiveExam();       // 今どの資格を見ているか
  const tasks = await getTasks(activeExam.id);    // そのタスク一覧

  return (
    <div>
      {tasks.map((task) => (
        <div key={task.id}>{task.title}</div>
      ))}
    </div>
  );
}

page.tsxの関数にasyncがついているのがポイントです。サーバーコンポーネントはasync functionにでき、その中で直接awaitしてデータベースからデータを取ってこられます。これも「フロントとバックが1つになっている」Next.jsらしい書き方です。

ステップ4：タスクを追加する（tasks/actions.ts）

src/app/(app)/tasks/actions.ts（抜粋）
"use server";

export async function createTask(formData: FormData) {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) return;

  const examId = formData.get("exam_id") as string;
  const title = (formData.get("title") as string)?.trim();
  if (!examId || !title) return;

  await supabase.from("tasks").insert({ user_id: user.id, exam_id: examId, title });
  revalidatePath("/tasks");   // 画面のデータを最新に更新
}

revalidatePath("/tasks")が重要です。データを追加しただけでは画面は自動更新されないので、「/tasksのデータは古くなったので、次に見るときは取り直してね」とNext.jsに伝えています。

他の機能（学習記録・教材管理・単語帳など）も、基本的にこの4ステップ（レイアウトでログイン確認 → queries.tsでデータ取得 → page.tsxで表示 → actions.tsで更新）の繰り返しです。1つの機能の流れを理解すれば、他の画面もほぼ同じパターンで読めます。

4. 「資格の切替」はどう実現しているか

このアプリの特徴的な設計に「複数資格を並行管理し、いつでも切り替えられる」というものがあります。これはCookieを使って実現しています。

src/lib/exams/active.ts
export async function getActiveExam(): Promise<Exam | null> {
  const exams = await getExams();               // 自分が登録した資格一覧
  if (exams.length === 0) return null;

  const cookieStore = await cookies();
  const cookieId = cookieStore.get("active_exam_id")?.value;
  return exams.find((e) => e.id === cookieId) ?? exams[0];  // 見つからなければ先頭にフォールバック
}

「資格管理」画面で「この資格に切替」ボタンを押すと、active_exam_idというCookieにその資格のIDが保存されます。以降、ほぼ全てのページで最初にgetActiveExam()を呼び、それを起点にデータを絞り込んでいます（例：getTasks(activeExam.id)）。

専用のテーブルを作らずCookieだけで実現しているのがポイントです。ログインと同じ仕組みで扱えるため、余計なテーブル・複雑さが増えません。

5. ログインの仕組み

Googleログインの流れは次のようになっています。

  1. 「Googleでログイン」ボタン → Server Action signInWithGoogle() が実行される
  2. Supabaseに「Googleでログインしたい」とリクエストし、Googleのログイン画面のURLをもらって、そこにリダイレクトする
  3. ユーザーがGoogleでログインすると、Googleは/auth/callbackというURLに「認証コード」付きで戻してくる
  4. /auth/callback/route.tsがその認証コードを本物のログインセッション（Cookie）に交換する
  5. 以降のアクセスでは、src/proxy.ts（ミドルウェア）が毎回セッションの有効期限を確認・更新する

この「毎回セッションを確認する」役割を持つのがsrc/proxy.tsです。Next.js 15まではmiddleware.tsという名前でしたが、Next.js 16からはproxy.tsという名前に変わりました（機能は同じです）。

6. データベース設計の要点

詳細はデータ設計書にER図とテーブル定義がありますが、コードを読むうえで知っておくと良い点だけ挙げます。

  • データは 資格(exams) → 科目(subjects) → 教材(materials) → 単語(words) という親子関係になっている
  • 単語の「タグ」は多対多（1つの単語に複数タグ、1つのタグを複数単語に）なので、tagsテーブルとword_tagsという中間テーブルの2つに分かれている
  • 「復習」は単語 or 教材のどちらか一方だけを対象にする、という制約がテーブル自体（CHECK制約）にかかっている

7. 開発中に遭遇した不具合と直し方（実体験）

実際に開発中にハマったバグを2つ紹介します。動くコードを読むだけでなく「なぜそう書かれているか」を知ると理解が深まりますし、面接で「苦労した点は？」と聞かれたときにそのまま使える話です。

7.1 タイムゾーンのバグ（連続学習日数が0日と表示される）

症状：今日90分勉強したのに、ダッシュボードの「連続学習日数」が0日と表示された。

原因は、日付を文字列にする処理でDate.toISOString()を使っていたことでした。この関数は協定世界時（UTC）に変換してから文字列にします。サーバーは日本時間（JST、UTC+9）で動いているため、「日本時間の今日0時」は「UTCでは昨日の15時」になり、日付が1日ずれていました。 

// バグがあった書き方
d.toISOString().slice(0, 10)   // UTCに変換されるため日付がずれる

// 直した書き方（ローカルの年月日をそのまま使う）
`${d.getFullYear()}-${String(d.getMonth()+1).padStart(2,"0")}-${String(d.getDate()).padStart(2,"0")}`

この修正はsrc/lib/dates.tsのtoDateStr()関数にまとめてあり、日付を文字列化する処理は必ずこの関数を通すようにしています。

7.2 Turbopack本番ビルドのByteStringエラー

症状：ローカルでは問題なくログインできるのに、Vercel本番環境だけ「Cannot convert argument to a ByteString...」というエラーでログインが失敗する。

調査の結果、Supabaseのログイン処理（exchangeCodeForSession）が内部でサーバー間通信のヘッダーを組み立てる際に、Next.js 16のTurbopack本番ビルド特有の不具合でエラーになっていることが分かりました（next devでは再現しない）。ローカルの本番ビルド（next build && next start）でも再現することを確認し、原因を「アプリ側の設定ミス」ではなく「ビルドツールの不具合」だと切り分けました。

最終的な対処は、ライブラリの内部処理を使わず、自分でPKCE認証コードの交換処理を書くsrc/app/auth/callback/route.ts）。

このバグ調査は、「ローカルでは動くが本番だけ動かない」ときにどう切り分けるかの良い実例です。①ローカルで本番相当のビルドを再現する、②公式ドキュメント・既知のIssueを検索する、③ライブラリ内部を信頼しすぎず自前実装に置き換える、という手順を踏みました。

8. 用語集

9. 面接で聞かれそうな質問と答え方のヒント

Q. なぜこの技術構成（Next.js + Supabase）を選んだのですか？
A. 個人開発なので運用負荷を抑えたかったこと、データが「資格→科目→教材→単語」というリレーショナルな構造を持つためPostgreSQLと相性が良いことを、技術選定書で他候補（Firebase等）と比較して決めた、と説明できます。
Q. サーバーコンポーネントとクライアントコンポーネントはどう使い分けましたか？
A. 基本は全部サーバーコンポーネントにし、ブラウザでしか動かせない処理（グラフ描画、現在地のハイライト表示）だけクライアントコンポーネントにした、と本書2.1節の内容で説明できます。
Q. セキュリティ面で工夫した点は？
A. 全テーブルにRow Level Security（RLS）を設定し、「自分のデータしか見えない・操作できない」をアプリのコードではなくデータベース側で強制している点。アプリ側にバグがあっても他人のデータ漏洩を防げる設計にした、と説明できます。
Q. 開発で一番苦労した点は？
A. 本書7章のTurbopackのByteStringバグの話がそのまま使えます。「ローカルでは再現しないが本番だけ失敗する」問題を、公式ドキュメントを読む・ローカルで本番相当の環境を再現する・原因を切り分けて自前実装に置き換える、という手順で解決したこと。
Q. データベース設計で工夫した点は？
A. 「資格」を全データの起点とする階層構造にしたこと（データ設計書参照）。単語帳のタグは多対多関係として中間テーブルで表現したこと。復習対象が単語/教材のどちらか一方であることをアプリ側だけでなくDBのCHECK制約でも保証したこと。
Q. テストは書きましたか？
A. 正直に「自動テストは未整備」と答えつつ、代わりに機能追加のたびにブラウザで実際に操作して動作確認する運用にしていたこと、今後の改善点として認識していることを伝えるのが誠実です。
