資格勉強向け学習管理アプリ データ設計書

作成日：2026年7月23日　／　対象：要件定義書 v2・技術選定書 v2 に基づくデータ設計

1. 本書の位置づけ

本書は「要件定義書」で定義した機能要件（特に4.1 資格管理・切替で決定した「資格 → 科目 → 教材 → 単語」の階層構造、複数資格の並行管理）と、 「技術選定書」で採用した Supabase（PostgreSQL）を前提に、実装に着手できる粒度までテーブル構造を具体化したものである。 実装フェーズの最初のステップとして、コードを書く前にこの設計を確定させる。

4. RLS（Row Level Security）方針

  • 上記すべてのテーブルで RLS を有効化する（word_tags は words 経由での間接チェックも可）
  • 基本ポリシーは全テーブル共通で user_id = auth.uid() を select / insert / update / delete すべてに適用する
  • insert 時は user_id を常にログインユーザーのIDで設定する（クライアントから任意の user_id を渡せないようにする）
  • word_tags のように user_id を持たない中間テーブルは、親テーブル（words または tags）の user_id をサブクエリで参照するポリシーにする

5. インデックス方針

  • 全FKカラム（exam_id・subject_id・material_id・word_id・tag_id）に単体インデックスを作成
  • study_logs(user_id, study_date)：ダッシュボードの「今日／今週の学習時間」「連続学習日数」集計、学習履歴の絞り込みで使用
  • reviews(user_id, scheduled_date, status)：復習管理の「未実施一覧」表示で使用
  • words(user_id, is_resolved)：単語検索の「未解決のみ表示」フィルタで使用
  • tasks(exam_id, is_done)：ダッシュボード・タスク管理の未完了タスク表示で使用

6. 今後の検討事項

  • 単語帳の「全資格横断表示」（4.6）は、words → materials → subjects → exams のJOINで都度絞り込む設計とした。件数増加時にパフォーマンスが問題になる場合は、words・materials に exam_id を非正規化して持たせることを検討する
  • 復習実施時に理解度の変更履歴（いつ・どう変わったか）を残す必要があるかは未決定。必要になった場合は review_logs 等の履歴テーブルを別途追加する
  • 連続学習日数（ストリーク）の判定ロジック（何時間以上で「学習した日」とみなすか、タイムゾーンの扱いなど）は詳細設計で別途定義する
  • タスク（3.5）を資格に紐づけず、資格をまたいだ横断タスクとして扱いたいケースが出てきた場合は、exam_id を null許容に変更する
  • 将来拡張（通知・AI解説・バッジ）に伴うテーブル追加（例：notifications、badges）は本設計のスコープ外とし、必要になった時点で追記する
